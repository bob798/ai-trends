> 📍 **本文视角**：从「能力是可调度资源」角度读 LLM 路由——它把"模型选型"从一次性架构决策变成了每条 query 的实时优化。**不是**路由算法教程、**不是** RouterArena 榜单解读。要复现/调参细节请看 [论文原文](https://arxiv.org/abs/2605.30736)。
>
> **适合的读者**：在"开源/弱模型 + 偶尔调用前沿"之间做成本-质量权衡、考虑自建路由层的人。

# 一句话核心

> **路由把"用哪个模型"变成一个可学习、成本感知的调度决策——能力不再是单一模型的固定属性，而是模型池里可按 query 动态分配的资源。但路由只「分配」能力、不「创造」能力：池子里没有旗舰，再聪明的路由器也变不出旗舰的表现。**

# 模型基本盘（速览）

> 这是一篇**生产导向的工程技术报告**，作者明确"不提出新 bandit 算法"。最小 context 如下，方法细节见原文。

|  | OrcaRouter |
|---|---|
| **是什么** | 生产级 LLM 路由器：请求生成**之前**就决定派给 10 个模型里的哪一个 |
| **方法** | 经典 LinUCB 上下文老虎机；每模型一个 ridge arm；特征 = 40 维词法 + 384 维 MiniLM 句向量 = 424 维 |
| **训练范式** | 离线"全信息"热身（每模型都在一批 prompt 上跑出 reward 矩阵 → 闭式 ridge 初始化）+ 可选在线 bandit 更新（只更新被选 arm） |
| **奖励** | r = w_q·质量 − w_c·成本 − w_ℓ·延迟 − 运营惩罚（限流/格式错误） |
| **结果** | RouterArena（8400 题，10 模型池）**排名 #2**，Arena 72.08，**75.54% 准确率 @ $1.00/1K** |
| **对照** | 永远选 DeepSeek-chat：70.31 @ $0.10/1K；Oracle 上限：80.72 |
| **模型池** | Claude Haiku 4.5 / Sonnet 4、Gemini 2.5 Flash/Flash-Lite、GPT-4o-mini / GPT-5-mini、DeepSeek-chat/reasoner、Qwen3 235B/30B（**无旗舰**：无 Opus/Fable 5/GPT-5 full） |

**复核窗口**：单一基准（RouterArena）结论，需看含旗舰模型池、其他路由基准上的复现后再加权。

# 为什么这是个信号

模型数量与价位正在爆炸式分化（two-SKU 发布进一步加剧），"选哪个模型"本身已经成为一个**独立的优化问题和产品层**。OrcaRouter 证明：用 2010 年的经典 bandit 就能做到 RouterArena #2——**路由的工程门槛不高、价值明确**。这预示"模型路由层"会沉淀为标准基础设施，正是 [Fable/Mythos 5 双 SKU 信号](2026-06-09-anthropic-fable-mythos-5.md)预言过的"在不同模型/SKU 间动态切换的路由层"。

# 核心观点

| # | 观点 | 论据 | 适用判断 |
|---|------|------|---------|
| 1 | **路由是"生成前"决策，信息天然稀缺** | 不同于 reward modeling（生成后打分），路由只有 request + 模型元数据 | 别指望路由器有"看了答案再选"的精度 |
| 2 | **离线全信息热身 > 在线 bandit 自适应（在本基准上）** | 部署版 72.08 反而**低于**纯离线 ridge 拟合 74.05 | "在线自适应"是卖点也是问号——先验证它真带来增益 |
| 3 | **多花 10× 成本换约 5 个点** | 75.54%@$1.00/1K vs 永远选 DSC 的 70.27%@$0.10/1K | 路由价值高度取决于你的成本敏感度，不是无脑划算 |
| 4 | **鲁棒性是软肋** | 同义改写下 Arena 鲁棒分仅 22.62；pick-flip 16.7%；margin 兜底可压到 2.4%（代价 −0.86 分） | 真实分布漂移大的场景，embedding 路由会抖 |
| 5 | **路由只分配、不创造能力** | 移除上下文特征后路由器塌缩成"永远选 DeepSeek-chat" = 硬编码单模型 | 池里没有 Fable 5，路由再优也够不到 Fable 5 |

# 可复用框架

## 框架 A：生产级路由的三件套要求

作者提炼的、判断一个路由系统是否"生产可用"的三条：①**可变模型池**（能随时纳入新模型）；②**适应请求分布漂移**；③**持续在线更新**（每服务一条就能精修策略）。缺一条都只是 demo。

## 框架 B：成本感知奖励 = 把质量/成本/延迟/可靠性压成一个标量

`r = w_q·质量 − w_c·成本 − w_ℓ·延迟 − 惩罚`。这个结构可直接搬到任何"质量-成本权衡"的调度问题（不止 LLM）。权重就是你的业务偏好旋钮。

## 框架 C："Oracle gap"作为路由系统的标尺

评估一个路由器，不要只看绝对准确率，要看**离"池内每题选最优"的 Oracle 上限还有多远**（这里 72.08 vs 80.72，gap≈8.6）。Oracle gap 把"路由器有多笨"和"池子有多强"解耦开。

# 金句

> 在路由里，决策必须在生成之前做出。（"the decision must be made before generation"）

# 我的延展

- **对从业者的启示**：路由是"开源/弱模型打底 + 难题才调用前沿"这一成本最优解的**工程实现**。但上线前先量化两件事：你的 **Oracle gap**（路由还能榨多少）和**成本曲线斜率**（多花的钱换几个点）。本文还提示：**先把离线全信息热身做扎实，在线自适应未必值得**。
- **对趋势判断的启示**：two-SKU + 模型爆发 → **模型路由层会成为新的基础设施层**，第三方路由 SaaS（如 OrcaRouter 自身）是可预期的赛道。
- **反对意见 / 盲点**：
  - 这是 applied report，**非新方法**（LinUCB 是 2010 年的），且**排第 2 不是第 1**；学术新意有限，价值在工程整合。
  - **在线自适应在本基准未显增益**——论文最大卖点之一（hybrid online learning）在数据上站不太住。
  - 模型池里**没有任何旗舰**，结论能否外推到"含 Fable 5 的池"未知——而那才是和本仓库主线最相关的场景。
  - 单一基准 + 鲁棒性差（22.62），对真实生产的分布漂移可能比榜单脆弱得多。
